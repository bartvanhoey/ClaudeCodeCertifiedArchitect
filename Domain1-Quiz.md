## Task Statement 1.1 — Agentic loops

**Q1.** An agent's control loop checks `if "done" in response.text.lower(): break`. What's wrong with this design, and what should replace it?

<details><summary>Answer</summary>
It parses natural language as a control signal — brittle and unreliable (Claude may say "done" mid-explanation without meaning to terminate, or finish without using that word). Replace with checking <code>response.stop_reason == "end_turn"</code>.
</details>

**Q2.** True or false: Claude executes the tool itself when it returns a `tool_use` block.

<details><summary>Answer</summary>
False. Claude only requests a tool call. The client/application code is responsible for actually executing it and returning a <code>tool_result</code>.
</details>

**Q3.** Why is a max-iteration cap still recommended even though it shouldn't be the primary stop condition?

<details><summary>Answer</summary>
As a safety bound against runaway loops (cost, infinite loops from a confused agent) — a backstop, not the intended termination mechanism.
</details>

**Q4.** In the message array, what role is used to send `tool_result` blocks back to Claude?

<details><summary>Answer</summary>
<code>"user"</code> — tool results are sent as user-role messages, even though they're generated by your code, not a human.
</details>

## Task Statement 1.2 — Coordinator–subagent orchestration

**Q1.** A coordinator always invokes Search → Analysis → Synthesis for every incoming query, regardless of complexity. What's the problem?

<details><summary>Answer</summary>
It's not dynamically selecting subagents based on query needs — this wastes cost/latency on simple queries and is the opposite of the "analyze requirements, select subagents" skill the exam wants. A good coordinator decides per-query.
</details>

**Q2.** Two subagents need to exchange information mid-task. What's the correct architecture?

<details><summary>Answer</summary>
They should not talk directly — the information must be routed through the coordinator (hub-and-spoke), which forwards/relays as needed.
</details>

**Q3.** A coordinator decomposes "analyze the effects of remote work" into exactly two subagent tasks: "productivity data" and "employee satisfaction data." The final report is thin. What likely went wrong, and whose responsibility was it?

<details><summary>Answer</summary>
Overly narrow task decomposition by the coordinator — the split missed facets like real estate/commercial impact, management practices, or economic effects on cities. This is a coordinator-level risk, not a subagent execution failure.
</details>

**Q4.** After synthesis, the coordinator notices the report lacks any cost data. What's the correct next step per the iterative refinement pattern?

<details><summary>Answer</summary>
Re-delegate to a search (and possibly analysis) subagent with a targeted query specifically about cost data, then re-run synthesis — not restart the entire pipeline from scratch.
</details>

## Task Statement 1.3 — Subagent invocation, context passing, spawning

**Q1.** A coordinator's `allowedTools` list is `["WebSearch", "Read", "Write"]`. It tries to spawn a subagent. What happens?

<details><summary>Answer</summary>
It can't — <code>"Task"</code> is missing from <code>allowedTools</code>. The Task tool must be explicitly allowed for a coordinator to invoke subagents at all.
</details>

**Q2.** A coordinator spawns a synthesis subagent with the prompt "Summarize the findings." No findings are included in the prompt. What will happen, and why?

<details><summary>Answer</summary>
The subagent has no findings to summarize and no way to retrieve the coordinator's conversation history — it starts with isolated/cold context. It will likely hallucinate, ask for clarification, or produce an empty/generic response. The findings must be explicitly included in the prompt text.
</details>

**Q3.** Three independent search subagents need to run concurrently. How should the coordinator invoke them?

<details><summary>Answer</summary>
Emit all three Task tool calls within a single coordinator response/turn, not as three separate sequential turns.
</details>

**Q4.** Why pass findings between subagents as structured data (content + source metadata) rather than a single free-text blob?

<details><summary>Answer</summary>
To preserve attribution — so downstream agents (e.g., synthesis) can correctly cite sources, page numbers, and document names rather than losing or scrambling that information when it's all mashed into prose.
</details>

**Q5.** Should a coordinator's prompt to a research subagent read like a numbered step-by-step script, or a statement of goals and quality bar? Why?

<details><summary>Answer</summary>
Goals and quality bar — this preserves subagent adaptability so it can adjust its approach based on what it actually discovers, instead of being locked into a procedure that may not fit.
</details>

## Task Statement 1.4 — Multi-step workflows: enforcement and handoff

**Q1.** A support agent's system prompt says "Always verify the customer's identity before issuing a refund." Is this sufficient for a financial compliance requirement?

<details><summary>Answer</summary>
No — prompt instructions have a non-zero failure rate. A compliance-critical ordering requirement needs programmatic enforcement (e.g., a hook/gate blocking <code>process_refund</code> until verification is confirmed in code-tracked state).
</details>

**Q2.** What's the mechanism to guarantee `process_refund` can never be called before `get_customer` succeeds?

<details><summary>Answer</summary>
A programmatic prerequisite gate (hook) that checks state and blocks the tool call — not a prompt instruction.
</details>

**Q3.** A customer emails about three unrelated issues in one message. What's the correct workflow pattern?

<details><summary>Answer</summary>
Decompose into distinct items, investigate each in parallel with shared context, then synthesize one unified response — not three separate uncoordinated replies or handling only the first issue mentioned.
</details>

**Q4.** When escalating to a human agent, why must the handoff include root cause analysis and not just "customer is upset about a charge"?

<details><summary>Answer</summary>
Because the human agent has no access to the conversation transcript — the handoff must be self-contained enough for them to act without redoing the investigation.
</details>

## Task Statement 1.5 — Agent SDK hooks

**Q1.** An MCP tool returns `status: 2` while another returns `status: "shipped"` for the same concept. What hook pattern addresses this, and at what point in the pipeline?

<details><summary>Answer</summary>
A <code>PostToolUse</code> hook, applied after the tool executes and before Claude processes the result — normalizing both into a consistent format.
</details>

**Q2.** Business policy: refunds above $500 must always be escalated to a human, no exceptions. Should this be implemented as a prompt instruction or a hook? Why?

<details><summary>Answer</summary>
A hook (tool-call interception) — because prompt instructions are probabilistic and have a non-zero failure rate, which is unacceptable for a "no exceptions" business rule. The hook blocks the call deterministically and redirects to escalation.
</details>

**Q3.** What's the difference in *when* a PostToolUse hook fires versus a tool-call interception hook?

<details><summary>Answer</summary>
PostToolUse fires after a tool has executed, operating on its result (for transformation/normalization). Tool-call interception fires before execution, operating on the proposed call itself (for blocking/redirecting).
</details>

**Q4.** True or false: hooks and prompt instructions achieve the same reliability, so the choice is just style preference.

<details><summary>Answer</summary>
False. Hooks are deterministic (code-level guarantee); prompts are probabilistic (model-level, non-zero failure rate). The choice matters whenever compliance must be guaranteed.
</details>

## Task Statement 1.6 — Task decomposition strategies

**Q1.** A code review task involves 15 files. Why not just ask Claude to review "all 15 files and their interactions" in one shot?

<details><summary>Answer</summary>
Attention dilution — trying to hold local per-file analysis and cross-file interaction reasoning simultaneously across 15 files degrades quality. Better: per-file passes (prompt chain) plus one dedicated cross-file integration pass.
</details>

**Q2.** "Add comprehensive tests to this legacy codebase" — should this use a fixed sequential pipeline or dynamic decomposition? Why?

<details><summary>Answer</summary>
Dynamic/adaptive decomposition — the high-impact areas and dependency order aren't knowable up front; the plan must adapt as structure-mapping and testing reveal new information.
</details>

**Q3.** What's the defining difference between prompt chaining and dynamic decomposition?

<details><summary>Answer</summary>
Prompt chaining is a fixed, predetermined sequence of steps known in advance. Dynamic decomposition generates subtasks based on intermediate findings — the plan isn't fully known until execution is underway.
</details>

**Q4.** A reviewer wants a "cross-file integration pass." What does that step specifically check for, that per-file passes miss?

<details><summary>Answer</summary>
Interactions, consistency, and architectural issues across files — things invisible when each file is analyzed in isolation.
</details>

## Task Statement 1.7 — Session state, resumption, forking

**Q1.** You paused an investigation session two days ago. Nothing in the codebase has changed. How should you continue?

<details><summary>Answer</summary>
<code>--resume &lt;session-name&gt;</code> — prior context is still valid, no need to re-explore or start fresh.
</details>

**Q2.** You want to compare a "test with mocks" strategy against a "test with a real DB" strategy, both starting from the same already-completed codebase analysis. What mechanism fits?

<details><summary>Answer</summary>
<code>fork_session</code> — branch into two independent explorations from the shared baseline, avoiding redundant re-analysis and cross-contamination between the two strategies.
</details>

**Q3.** You resume a session from last week, but three files it previously analyzed have since been substantially rewritten. What's the best next step — resume and proceed normally, resume and inform it of the specific changes, or start fresh?

<details><summary>Answer</summary>
Resume, but explicitly inform the agent which files changed and how — enabling targeted re-analysis of just those files, rather than either trusting stale results or paying for a full re-exploration.
</details>

**Q4.** Why might starting a new session with a structured summary be more reliable than resuming a session with extensively stale tool results?

<details><summary>Answer</summary>
Resuming carries forward the full history of now-incorrect tool results, and the agent may keep reasoning from them. A fresh session with a clean, structured, accurate summary avoids inheriting bad assumptions baked into stale conversation history.
</details>

## Mixed review round (no task numbers — identify the concept yourself)

**M1.** A workflow scenario says a step "must never" be skipped for compliance reasons. What implementation approach does that phrasing point to?

<details><summary>Answer</summary>
Programmatic enforcement (a hook / prerequisite gate) — "must never" signals a deterministic-guarantee requirement, which prompts alone cannot provide.
</details>

**M2.** A coordinator spawns Subagent B, whose prompt references "the analysis from Subagent A" without including that analysis's actual content. What will go wrong?

<details><summary>Answer</summary>
Subagent B has isolated context and never automatically receives Subagent A's output — referencing it by name isn't enough. The actual findings must be included directly in Subagent B's prompt text.
</details>

**M3.** Which is the correct stop signal for an agentic loop: presence of assistant text, a fixed iteration count, or `stop_reason`?

<details><summary>Answer</summary>
<code>stop_reason</code> (specifically <code>"end_turn"</code>) — the only structured, authoritative signal. Text presence and iteration counts are anti-patterns as primary stop mechanisms.
</details>

**M4.** A single coordinator response contains three `Task` tool_use blocks. What execution pattern does this represent?

<details><summary>Answer</summary>
Parallel subagent spawning — multiple Task calls emitted in one turn run concurrently, as opposed to sequential spawning across separate turns.
</details>

**M5.** Research topic decomposed into only two narrow subagent tasks, resulting in a report with major gaps. What's this risk called, and which task statement covers it?

<details><summary>Answer</summary>
Overly narrow task decomposition by the coordinator (Task Statement 1.2) — a coordinator-level risk of incomplete topic coverage, distinct from any individual subagent underperforming.
</details>

**M6.** A hook fires after a tool executes and rewrites its output into a consistent format before Claude sees it. Name the hook pattern and its purpose.

<details><summary>Answer</summary>
PostToolUse hook — used for data normalization (e.g., reconciling inconsistent timestamp/status formats across different MCP tools).
</details>

**M7.** An open-ended task like "modernize this legacy module" is given a rigid five-step plan up front, and the plan doesn't adjust when unexpected dependencies are discovered mid-task. What decomposition mistake is this?

<details><summary>Answer</summary>
Applying fixed prompt chaining to a task that requires dynamic/adaptive decomposition — the plan should have been generated/adjusted based on intermediate findings, not fixed in advance.
</details>

**M8.** You're about to resume a session whose prior tool results are almost entirely stale due to major changes since last use. What's more reliable than resuming?

<details><summary>Answer</summary>
Starting a new session and injecting a structured summary of what's currently known/true, rather than resuming and inheriting a conversation history full of stale tool results.
</details>
